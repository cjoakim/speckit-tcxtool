## R1. The 16-field States CSV

**Decision**:
- `StatesCsvRow` gets 16 positional properties, in the FR-002 order, and `DistanceMiles` becomes
  `StateDistanceMiles`.
- `StatesCsvWriter.Header` and `FieldCount` (16) change, and `Write` writes the fields in record order.
- `Rows` adds three values:
  - `StateTrackpointCount`: `set.Count`, written with `CultureInfo.InvariantCulture`.
  - `ActivityDistanceMiles`: `LastNonEmpty(set, row => row.DistanceMiles)`.
  - `ActivityElapsedSeconds`: `LastNonEmpty(set, row => row.ElapsedSeconds)`.
- Every other value's rule is unchanged (FR-003).

**Rationale**:
- The two activity values follow the spec's "last row that has one, as written" rule. That is the
  rule `ActivityElapsedTime` already uses, so the code reuses `LastNonEmpty`.
- Copying the text keeps the 006 rule that end values are copied, not recalculated (006 research R2).
  The last row's ActivityDistanceMiles is then byte-identical to the activity CSV's last DistanceMiles
  (SC-001).
- Positional records in file order make a field-order mistake visible at every construction site.

**Alternatives considered**:
- *`LastFinite` and reformatting for ActivityDistanceMiles*: this could change the digits, for no
  benefit.
- *Leaving the property order alone and reordering only in `Write`*: the record would no longer
  match the file, and every test that builds rows would read out of order.

## R2. Golden files and the generator

**Decision**: `generate_success_fixtures.py`'s `states_rows()` adds the three values and writes the
16 fields in the new order. All 8 `Expected/*.states.csv` files are regenerated by it, never by the
converter. The activity goldens don't change, and the generator must leave them byte-identical, which
is checked with `git diff --stat`.

**Rationale**: this is the independent-calculation rule from feature 002, and 006 lesson R12. The
count is `len(set)`, and the two activity values use the generator's existing `last_value()`. No
sums are needed, so the `sum()` trap can't occur.

**Alternatives considered**: *editing the goldens by hand*: that is error-prone for 8 files, and
breaks the rule that the generator is the source.

## R3. Old 13-field States CSVs

**Decision**: nothing new. `StatesCsvReader` checks the header against `StatesCsvWriter.Header`, so
a 13-field file is a `HeaderMismatch`. `CurrentStatesLoader` turns that into `WrongFormat`, and both
pages show the existing wrong-format notice with its Convert link (FR-006). A test proves it with a
13-field file built from the 006 header.

**Alternatives considered**: *reading both formats*: rejected by the spec (Assumptions), and it
would be the only dual-format reader in the app.

## R4. Where the Timeline geometry is calculated

**Decision**: a Web-side `Timeline/TimelineLayout` builds the whole drawing as numbers, from the
`StatesCsvRow`s:
- every segment's start, width, and center, as **fractions of the bar** (0 to 1)
- every chart's domain (minimum and maximum)
- every chart's points (center fraction and value)

The browser script only multiplies fractions by the measured width and draws. It does no data
calculation.

**Rationale**:
- Principle V needs test-first tests that run in `dotnet test` with no live browser. With the
  geometry in C#, FR-012, FR-013, FR-019, FR-020, and FR-021 are plain unit tests.
- Fractions don't depend on pixels. Alignment (FR-018, SC-003) then holds by construction: the bar
  and charts use one measured width and the same left margin, so `x = margin + fraction × width`
  is the same for all four.
- It is presentation geometry, not parsing, so it belongs in the Web project, like `TrackpointBands`
  (Principle III).

**Alternatives considered**:
- *Calculating in D3 with `d3.scaleLinear` over the raw rows*: this is the usual D3 style, but the
  rules would be testable only in a browser.
- *A JavaScript test runner*: Node isn't in the test image, the test container has no network, and
  adding Node to the `Dockerfile` would change Principle VI's images for a test-only tool.
- *Jint (a .NET JavaScript engine)*: it adds a package and still has no DOM. The rules that need
  testing are arithmetic, and C# covers those.
- *The parser library*: it parses and converts files. Bar fractions are a UI concern.

## R5. Segment widths (FR-013)

**Decision**:
- `seconds(set)` is StateElapsedSeconds parsed as invariant `double`. It is used only when finite and
  ≥ 0, and otherwise counts as 0.
- `total` is the left-to-right sum of `seconds` over all sets.
- When `total > 0`:
  - `start(i)` is the sum of `seconds(0..i-1)` over `total`
  - `width(i)` is `seconds(i)` over `total`
  - `center(i)` is `start(i) + width(i) / 2`
- When `total` is 0 (for example, a one-trackpoint activity), every set gets the same width, `1/n`,
  so the bar is still filled.
- The last segment's end is set to exactly 1, so rounding can't leave a sub-pixel gap.

**Rationale**:
- Q1 answer A. StateElapsedSeconds adds up to the activity's elapsed time (006 contract), so the bar
  is the activity's time. This is 19,881 s for the marathon.
- Summing instead of reading the last ActivityElapsedSeconds means the segments always fill the bar
  exactly (FR-012), even if a value is missing.

**Alternatives considered**:
- *Scaling by the last ActivityElapsedSeconds*: a missing StateElapsedSeconds would leave a gap.
- *A minimum pixel width*: rejected. It breaks proportionality, and the Q1 answer made it
  unnecessary.

## R6. Chart domains and points (FR-019 to FR-021)

**Decision**:
- For each chart (AverageRunCadence, AverageHeartRateBpm, AverageAltitudeMeters), the values are the
  sets' fields parsed as invariant `double`, finite only. A set with no value has no point.
- The domain is `[min, max]` of the values. When `min == max`, it is `[v − 1, v + 1]`.
- A chart with no values has no domain, and the page shows its label and "No data." (edge case).
- Points keep StateSet order, and the line joins them in that order, so a skipped set joins its
  neighbours.

**Rationale**:
- Each chart has its own minimum and maximum, as the draft asks. D3's `.nice()` is not used, because
  it would extend the axis past the data, which FR-020 forbids.
- ±1 unit is a small, readable range for steps per minute, beats per minute, and meters.

**Alternatives considered**: *±5% of the value*: this breaks down at 0, for example a cadence of 0
in a stopped-only activity.

## R7. Handing the data to the browser

**Decision**:
- The page renders a custom element, `<tcx-timeline>`.
- Its `data-timeline` attribute holds the layout as JSON, from `System.Text.Json` with camelCase
  names. Blazor attribute-encodes the value.
- The script reads it with `JSON.parse(element.dataset.timeline)`.

**Rationale**:
- One request, and the page and data can't disagree.
- Attribute encoding makes any CSV text safe, including `"`, `<`, and `</script>`, with no
  `MarkupString`.
- The payload is about 150 KB for 541 sets, which is in line with the 187 KB States page.

**Alternatives considered**:
- *`<script type="application/json">`*: this is Razor error RZ9992, and suppressing it is forbidden.
- *A separate JSON endpoint*: a second request and a second route to test, and the page and data
  could disagree.
- *Writing one SVG on the server*: this can't follow the browser's width, and it isn't D3, which the
  constitution names for charts.

## R8. Loading the script with enhanced navigation

**Decision**:
- `App.razor` loads one small ES module, `wwwroot/js/timeline.js`, with
  `<script type="module" src="@Assets["js/timeline.js"]">`. It defines `tcx-timeline` with
  `customElements.define`.
- In `connectedCallback`, the element imports D3 on demand with
  `import(new URL("../lib/d3/d3.min.mjs", import.meta.url))`, then draws.
- `attributeChangedCallback` on `data-timeline` redraws.
- `disconnectedCallback` removes its `ResizeObserver` and document listener.

**Rationale**:
- Enhanced navigation patches the DOM without running page scripts. A custom element's callbacks run
  whenever the element is inserted or changed, so the page draws after both a full load and an
  enhanced navigation, with no `data-enhance-nav="false"` workaround.
- D3 (about 280 KB) is fetched only when a Timeline element exists, not on every page.

**To verify in implement**: an endpoint test checks that `/lib/d3/d3.min.mjs` is served with a
JavaScript content type. Static assets are served at their plain paths as well as the fingerprinted
ones. If that test fails, the fallback is a plain `<script src="@Assets["lib/d3/d3.min.js"]">` in
`App.razor`, with the module using the `d3` global.

**Implemented** (tasks.md T031 done note): the package's `d3.min.mjs` only re-exports bare `d3-*`
names, so it can't be imported in a browser. The module instead adds a classic `<script>` for the
vendored UMD `lib/d3/d3.min.js`, resolved against `import.meta.url`, the first time an element
connects, and uses the `d3` global. That keeps FR-022's one shared script reference and the
on-demand load. The plain-`<script>`-in-`App.razor` fallback above was not used.

**Alternatives considered**:
- *A `<script>` in the page*: it doesn't run after an enhanced navigation, and it is RZ9992.
- *Turning off enhanced navigation for the Timeline link*: one-off, and easy to lose.
- *A JS initializer listening for `enhancedload`*: more moving parts than a custom element.

## R9. Vendoring D3

**Decision**:
- Copy `d3.min.mjs` and `LICENSE` from the npm tarball `d3-7.9.2.tgz` into
  `src/JoakimSoftware.TcxTool.Web/wwwroot/lib/d3/`.
- First check the tarball's SHA-512 against npm's `integrity` value.
- `wwwroot/lib/d3/README.md` records the version, source URL, and checksum.
- A test checks that the file starts with `// https://d3js.org v7.9.2` and that `LICENSE` exists.

**Implemented**: `d3.min.js` (UMD, SHA-256 `912111098ea99503a6f4967361d2bbdc9dbf58cf9c678c8e27e5b02d1a07f0c1`)
in place of `d3.min.mjs`, for the reason in R8. The test checks `d3.min.js` instead.

**Rationale**:
- No CDN, so the app and tests need no network (FR-023). This is the same approach as Bootstrap.
- The ISC licence only asks for the notice to be kept, which the `LICENSE` file does.

**Alternatives considered**:
- *`d3.min.js` (UMD)*: kept only as the R8 fallback.
- *Individual `d3-*` modules*: more files to vendor for a 280 KB saving that doesn't matter locally.
- *libman or npm in the build*: needs network in the Docker build.

## R10. Drawing and alignment (FR-017, FR-018)

**Decision**:
- The server renders the containers inside `<tcx-timeline>`: the bar `div`, then per chart its
  label and a chart `div`, or "No data." when the chart has no points. The script draws into them.
- `<tcx-timeline>` holds four SVGs, stacked: the bar, then Run Cadence, Heart Rate, and Altitude.
- Each SVG is as wide as the element, which is measured once per draw with
  `getBoundingClientRect().width`.
- Every SVG uses the same margins: left 56 px for the y-axis labels, right 16 px. The plot width is
  `width − 72`.
- The bar is 32 px tall, with an elapsed-time axis under it (`h:mm:ss` ticks from
  `d3.scaleLinear([0, totalSeconds])`). Each chart is 140 px tall, with `d3.axisLeft` and 4 ticks.
- Points are circles of radius 2.5. The line is `d3.line()` with class `timeline-line`, which is
  `stroke: #adb5bd; stroke-width: 1px; fill: none`.
- A `ResizeObserver` redraws everything when the element's width changes.

**Rationale**:
- One width and one margin pair shared by all four drawings is what makes "same width, same left
  edge, aligned" true at every window size, including after a resize.
- A full redraw of about 2,200 marks takes milliseconds.

**Alternatives considered**: *one SVG with four groups*: equally aligned, but the chart labels and
"No data." notes are easier to add as HTML between separate SVGs.

## R11. The popup (FR-015, FR-016)

**Decision**:
- `pointermove` over the bar finds the segment under the pointer by `d3.bisector` over the segment
  starts.
  - If that segment is at least 4 px wide, it is the one.
  - Otherwise, the segment whose center is nearest the pointer, within ±4 px, is chosen. Ties go
    to the earlier segment.
  - This makes zero-width and sub-pixel segments, many of them short stops, reachable.
- A new segment fills one absolutely positioned `div.timeline-popup` (Bootstrap `card small shadow`),
  with a `dl` of the 16 field names and values, set through `textContent`.
- The popup stays open when the pointer leaves the bar.
- A `click` on the document outside the popup closes it.

**Rationale**:
- This follows the spec's Assumptions.
- `textContent` never interprets the CSV text as HTML.
- Bisecting by x is what the "very short StateSets" edge case needs.

**Alternatives considered**:
- *Bootstrap Popover*: needs a DOM anchor per segment, and closes on mouse leave.
- *`mouseenter` on each rect*: sub-pixel rects are hard to hit.

## R12. State colors in one place (FR-014)

**Decision**:
- `app.css` defines four custom properties on `:root`:
  - `--tcx-state-stopped: #6c757d`
  - `--tcx-state-walking: #ffc107`
  - `--tcx-state-running: #198754`
  - `--tcx-state-unknown: #dee2e6`
- It also defines classes `.state-stopped`, `.state-walking`, `.state-running`, and `.state-unknown`,
  which set `fill` and `background-color` from them.
- The script sets `class="timeline-segment state-…"`, using `state-unknown` for any other value, and
  never writes a color.
- A server-rendered legend under the bar uses the same classes.

**Rationale**:
- Q2 answer B.
- The legend explains the colors without hovering.
- Tests can check the four values in `app.css` (comments stripped first, a 005 lesson), and check
  that `timeline.js` has no hex color literal.

**Alternatives considered**: *colors in C# sent in the JSON*: a second place for them, and CSS is
where the band colors already live.

## R13. The header box (FR-010, FR-011)

**Decision**:
- A Web record `Timeline/TimelineHeader` (`FileName`, `ActivityId`, `Date`, `ActivityDistanceMiles`,
  `ActivityElapsedTime`), built by `TimelineHeader.From(csvFileName, rows)`.
- `Date` is the file name's first 10 characters when they parse as `yyyy-MM-dd` (invariant, exact),
  and empty otherwise.
- `TimelineHeaderCard.razor` copies the Table page's `ActivitySummaryCard` markup: a Bootstrap
  `card`, with `h2.card-title.h5` "Activity" and a `dl.row`. An empty value is a muted dash.

**Rationale**:
- The Home and Table cards are the same Bootstrap card, so the look matches with no new CSS.
- `CsvFileName` always writes that prefix (feature 002), but a hand-named file might not have it.

**Alternatives considered**: *reusing `ActivitySummaryCard`*: its fields are fixed to the activity
CSV (Device, Sport).

## R14. Notices shared with the States page (FR-008)

**Decision**:
- Move the `switch` of notices out of `StatesPage.razor` into `Components/States/StatesNotice.razor`,
  with parameters `Current` and `StatusId`.
- `StatesPage` and `TimelinePage` both render it, and the Loaded and NoStateSets content stays on
  each page.
- The Timeline page reuses `CurrentStatesLoader` and `CurrentStatesMessages`.

**Rationale**: "the same wording and links as the States page" holds by construction. The existing
`StatesPageTests` prove the move changes nothing.

**Alternatives considered**: *copying the switch*: two copies would drift.
